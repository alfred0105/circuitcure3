# Phase 21.3.2 — ONNX export contract

`python scripts/component_training.py export --weights path/to/best.pt --imgsz 640` exports to a sibling `export/` directory unless `--output` is set. It uses opset 17, exports without embedded NMS, validates with `onnx.checker`, loads with macOS ARM64 ONNX Runtime CPU, and records checkpoint/model hashes plus input/output names and shapes in a JSON file. It does not replace `models/pcb_component_detector.onnx`.

CircuitCare's existing decoder expects raw YOLOv8 detection output in `(1, 4 + class_count, candidates)` or transposed form: center-x, center-y, width, height in model-input pixels, followed by per-class scores; CircuitCare performs class-aware NMS and coordinate unletterboxing. Existing class order is in `src/circuitcare/vision/detection_postprocess.py`. A new model must use the same class count/order or an explicit compatible adapter before it can be used by the existing detector. Runtime input is RGB float32, normalized to [0,1], with 960px letterboxing for the deployed baseline.

Smoke and real-model export passed. The filtered YOLOv8n ONNX input is `[1,3,960,960]`, output `[1,14,18900]`, matching the existing ten-class raw YOLOv8 decoder contract; the smoke's two-class fixture used `[1,6,5376]`. ONNX checker and ONNX Runtime CPU load passed. The `verify_component_onnx.py` raw output comparison passed on one reviewed PCB image: max absolute error 0.00214, mean absolute error 0.0000123 (atol 0.0001, rtol 0.001). CircuitCare's existing evaluator successfully ran the existing baseline ONNX and the new ONNX. Export size was 12,992,171 bytes for the 960px new ONNX and 44,943,259 bytes for the baseline.

The single-image script routes ONNX to explicit `CPUExecutionProvider` and uses MPS only for `.pt` models. A synthetic one-image inference also ran through ONNX; the first run used Ultralytics' provider selection and initialized CoreML, so its 2.01-second cold-start latency is not a CPU benchmark. Use the evaluator measurements for comparable CPU latency. One-image raw parity is only an export sanity check, not a broad numerical equivalence guarantee. MPS training does not imply accelerated ONNX inference.
